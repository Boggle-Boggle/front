# 프로젝트 구조 컨벤션

## 문서 목적

이 문서는 빼곡 프론트엔드 프로젝트의 구조 규칙과 아키텍처 방향을 정의한다.

빼곡 프론트엔드는 레거시 코드의 기술 부채를 줄이기 위해 새로운 구조로 점진적으로 리팩토링하는 중이다. 따라서 새로 추가하거나 수정하는 코드는 일관된 구조 기준 위에서 작성되어야 한다.

## 프로젝트 방향

현재 코드베이스에는 구 버전 구현과 신규 구조가 함께 존재한다. 신규 작업은 레거시 구조를 확장하는 대신, 이후 유지보수와 확장이 쉬운 방향으로 쌓아가는 것을 원칙으로 한다.

이 문서의 구조 규칙은 다음 목표를 가진다.

- 라우트와 파일 구조를 쉽게 대응할 수 있게 만든다.
- 페이지 단위로 책임을 모아 변경 범위를 좁힌다.
- 지역 재사용과 전역 재사용의 경계를 분명하게 한다.
- 레거시 코드와 신규 코드를 안전하게 분리한다.

## 기술 스택

- React
- TypeScript
- TanStack Query
- Zustand
- Tailwind
- React Hook Form
- Zod

## 프로젝트 구조 원칙

### Page-based 구조를 기본으로 사용한다

빼곡 프론트엔드는 page-based 구조를 기본 단위로 사용한다. 페이지는 라우트와 가장 직접적으로 연결되는 단위이기 때문에, 화면과 관련된 로직과 UI를 페이지 폴더를 중심으로 구성하는 것을 우선한다.

페이지가 아니더라도 UI 또는 기능 단위가 명확하다면 폴더로 구조화할 수 있다. 예를 들어 섹션, 플로우, 스텝, 탭처럼 내부 책임이 분명한 경우에는 폴더 단위로 관리할 수 있다.

### 라우트 구조와 폴더 구조를 일치시킨다

라우팅 구조와 실제 폴더 구조는 가능한 한 같은 형태를 유지한다. 이 기준이 있어야 특정 URL이 어떤 페이지 코드와 연결되는지 빠르게 찾을 수 있다.

하위 라우트가 존재하는 경우에는 부모 페이지 폴더 내부에 동일한 구조의 하위 폴더를 둔다.

## 페이지 폴더 규칙

### 페이지는 폴더 단위로 만든다

모든 페이지는 파일 하나가 아니라 폴더로 생성한다. 페이지의 진입 파일뿐 아니라 해당 페이지 전용 로직, 하위 구성요소, 훅이 함께 자라날 수 있도록 기본 단위를 폴더로 둔다.

### 폴더 이름은 PascalCase를 사용한다

페이지와 컴포넌트 폴더 이름은 PascalCase를 사용한다.

허용 예시:

```tsx
src/pages/OrderDetail/
src/pages/SignUp/
```

### 엔트리 파일은 `index.tsx`를 사용한다

페이지 폴더의 진입 컴포넌트 파일은 `index.tsx`를 사용한다. 폴더명을 진입 이름으로 삼고, 파일명은 통일해서 탐색 비용을 줄인다.

허용 예시:

```tsx
src/pages/OrderDetail/index.tsx
src/pages/SignUp/index.tsx
```

## 폴더 내부 재사용 규칙

### 페이지 내부에서만 재사용되는 코드는 `shared/`에 둔다

특정 페이지 폴더 내부에서만 반복해서 쓰이는 컴포넌트나 로직은 전역으로 올리지 않는다. 이런 요소는 해당 폴더 안의 `shared/` 디렉터리에서 관리한다.

이 기준은 전역 디렉터리가 불필요하게 커지는 것을 막고, 페이지 단위 응집도를 높이기 위한 것이다.

허용 예시:

```tsx
src/pages/OrderDetail/
- index.tsx
- useOrderDetailState.ts
- shared/
  - Title.tsx
  - Content.tsx
```

### `shared/`는 폴더 스코프 공유만 허용한다

`shared/`는 같은 폴더 범위 안에서만 재사용되는 요소를 위한 위치다. 여러 페이지에서 함께 쓰이기 시작한 경우에는 `shared/`에 계속 두지 말고 전역 위치로 옮길지 검토해야 한다.

## 전역 디렉터리 배치 기준

여러 페이지에서 공통으로 사용하는 모듈은 아래 위치를 기준으로 관리한다.

- 전역 상태: `src/stores`
- 유틸 함수: `src/utils`
- 전역 훅: `src/hooks`
- 전역 컴포넌트: `src/components`

전역 디렉터리로 이동할 때는 “여러 곳에서 쓰인다”는 이유만으로 옮기지 말고, 재사용 범위가 실제로 프로젝트 전반인지 먼저 판단한다.

## 글로벌 컴포넌트 규칙

`src/components` 아래의 글로벌 컴포넌트는 스토리북 파일을 함께 포함해야 한다.

스토리북 파일은 컴포넌트와 같은 폴더에 둔다.

허용 예시:

```tsx
src/components/Button/
- index.tsx
- index.stories.tsx
```

## Legacy Protection

### 목적

`legacy` 디렉터리의 코드는 기존 시스템과의 호환성을 위해 유지되는 영역이다. 현재 리팩토링 범위는 이 영역을 직접 개선하는 것이 아니라, 신규 구조를 안전하게 쌓아가는 데 있다.

레거시 코드를 무심코 수정하면 타입, import, 런타임 동작, 기존 흐름과의 호환성에서 예기치 않은 사이드 이펙트가 발생할 수 있다.

### 보호 범위

아래 경로는 모두 보호 대상이다.

- `src/legacy/**`
- `legacy/**`

이 경로 아래의 파일은 모두 read-only로 취급한다.

### 허용되는 작업

아래 작업은 허용된다.

- 레거시 코드 읽기
- 분석을 위한 참조
- 신규 코드에서의 호환 레이어 설계 참고

### 금지되는 작업

아래 작업은 허용하지 않는다.

- legacy 파일 수정
- legacy 파일 포맷 변경
- legacy 파일 import 변경
- legacy 파일 props 변경
- legacy 파일 자동 리팩토링

다음과 같은 상황에서도 직접 수정하지 않는다.

- 새로운 코드 변경으로 import 에러가 발생하는 경우
- props 타입이 맞지 않는 경우
- 타입 에러가 발생하는 경우
- legacy 코드가 현재 컴포넌트를 import 하고 있는 경우
- 자동 리팩토링으로 정리 가능해 보이는 경우

### 충돌이 발생했을 때의 대응

레거시 코드와 신규 구조가 충돌할 경우, 우선순위는 레거시 수정이 아니라 신규 코드 쪽의 호환 처리다.

가능한 대응 방식:

- wrapper 추가
- adapter 추가
- 신규 코드에서의 호환 레이어 작성

레거시 자체를 수정해야만 해결되는 상황이라면, 그때 별도 승인과 범위 확인이 필요하다.
