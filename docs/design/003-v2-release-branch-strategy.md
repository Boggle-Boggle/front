# v2 출시와 v1 유지 기간의 브랜치·배포 전략

## 문서 목적

v2 앱 심사 및 출시 과정에서 기존 v1 사용자를 유지하기 위한 웹 브랜치와 도메인 운영 방식을 정의한다. 이 문서는 합의한 운영 설계이며, 브랜치 생성이나 호스팅 설정 변경이 완료되었다는 의미는 아니다.

## 배경 및 결정

- v1은 이미 스토어에 배포되어 있으며, 기존 앱 빌드는 구 도메인을 WebView로 연다.
- v2는 출시 예정이며, 신규 앱 빌드가 신규 운영 도메인을 열도록 구성한다.
- 구 도메인은 1월 만료까지 약 3개월간 유지하고 연장하지 않는다. 정확한 종료 일시는 별도로 확정한다.
- 유지 기간에는 v1 웹에서 종료일과 새 앱 업데이트 필요성을 안내하고 스토어 이동 버튼을 제공한다.
- v1 종료 전까지 기존 운영 브랜치를 개발용으로 전환하지 않는다.

## 브랜치 역할

| 브랜치 | 역할 | 배포 대상 | 허용하는 변경 |
| --- | --- | --- | --- |
| `master` | v1 운영 유지 | 구 도메인 | 업데이트 안내, 필요한 v1 긴급 수정 |
| `stg` | v2 개발 통합 및 출시 전 검증 | v2 테스트 환경 | v2 기능 개발, 버그 수정 |
| `prd` | v2 production 형상 | 신규 운영 도메인 | 검증된 출시 변경, 긴급 수정 |

이 문서의 `master`, `stg`는 합의한 역할 이름이다. 로컬 확인 시 실제 브랜치는 `main`, `staging`이었으므로, 실행 시 원격 브랜치와 호스팅 연결을 확인하고 기존 이름을 유지할지 변경할지 결정한다. 이름이 확인되지 않은 브랜치를 대상으로 작업하지 않는다.

v1 유지 기간에는 `master`에 v2 코드를 머지하지 않는다. 별도의 `legacy/v1` 브랜치는 이 전략에서 필요하지 않다.

## 앱과 웹 버전 분리

| 사용자 | 실행하는 앱 | 앱이 여는 도메인 | 제공되는 웹 |
| --- | --- | --- | --- |
| 기존 앱 사용자 | v1 빌드 | 구 도메인 | `master`의 v1 |
| v2 심사 담당자 | v2 제출 빌드 | 신규 운영 도메인 | `prd`의 v2 |
| 출시 후 업데이트 사용자 | v2 빌드 | 동일한 신규 운영 도메인 | `prd`의 v2 |
| 업데이트하지 않은 사용자 | v1 빌드 | 구 도메인 | 종료 전까지 v1 |

앱 빌드에 설정된 접속 URL로 버전을 분리한다. 웹에서 브리지 버전 유무를 검사해 v1과 v2를 선택하거나, 두 버전의 React 코드를 하나의 배포물로 합칠 필요가 없다.

심사 담당자를 식별해 다른 서비스를 제공하지 않는다. 심사 빌드와 출시 빌드가 동일한 v2 서비스를 사용하도록 한다. 브리지는 앱 정보 전달과 네이티브 기능 연동을 위한 별도 설계 대상으로 둔다.

## v2 개발 및 출시 흐름

1. v2 기능 브랜치를 `stg`에서 분기한다.
2. 작업한 변경을 `stg`에 통합하고 테스트 환경에서 검증한다.
3. 출시할 변경을 `stg`에서 `prd`로 반영한다.
4. `prd`를 신규 운영 도메인에 배포하고 해당 URL을 사용하는 앱 빌드를 검증한다.
5. 준비된 앱 빌드를 심사에 제출한다.

최초 `prd`는 검증된 `stg` 커밋에서 생성할 수 있다. 이 경우 최초 생성 직후 별도 머지는 필요하지 않다.

심사 중에는 `prd`의 기능 변경을 통제하고 다음 개발은 `stg`와 기능 브랜치에서 진행한다. 심사 대상 커밋과 앱 버전·빌드 번호를 기록한다. `prd`에서 긴급 수정한 경우 동일한 수정을 `stg`에도 반영한다.

## v1 유지 및 종료

### 유지 기간

구 도메인의 배포 연결은 기존 v1 운영 브랜치에 유지한다. v1 웹에 업데이트 안내, 종료일, 플랫폼별 스토어 링크를 제공한다. 지원 기간 동안 v1이 사용하는 API도 정상 동작해야 한다.

안내 기간에 앱을 실행하지 않은 사용자는 안내를 보지 못할 수 있다. 3개월 안내가 전체 사용자의 업데이트를 보장하지는 않는다.

### 도메인 만료 이후

도메인은 연장하지 않는다. 만료 이후에는 기존 앱에서 웹 콘텐츠와 업데이트 안내를 제공할 수 있다고 보장하지 않는다. 도메인 복구나 소유권 이전 상황에 따라 실패 화면 등 실제 증상은 달라질 수 있으며, v1은 지원 종료 상태로 취급한다.

기존 빌드에 대체 URL이나 네이티브 업데이트 안내 기능이 없다면, 서버에서 구 도메인을 거치지 않고 해당 앱의 접속 주소를 변경할 수 없다. 이 제약을 수용하고 유지 기간에 업데이트를 안내한다.

### 개발 브랜치 전환

1. 마지막 v1 운영 커밋을 태그로 보존한다.
2. 기존 v1 호스팅의 자동 배포 연결을 해제하고 서비스를 종료한다.
3. `master`를 v2 기준 개발 브랜치로 전환하거나 `dev`로 변경한다. 구체적인 브랜치 전환 방법은 당시 이력과 미반영 변경을 확인한 뒤 정한다.
4. 이후 `dev → stg → prd` 또는 `master(개발용) → stg → prd` 흐름으로 운영한다.

개발 브랜치의 최종 이름은 v1 종료 시 결정한다. v1 API 종료는 다른 클라이언트 사용 여부를 확인하고 별도로 진행한다.

## 실행 전 확인 사항

- [ ] 실제 v1 운영 브랜치와 배포 커밋을 확인한다.
- [ ] 실제 브랜치명과 구·신 도메인의 자동 배포 연결을 확인한다.
- [ ] v2 테스트 환경과 신규 운영 환경의 URL 및 환경 변수를 분리한다.
- [ ] 신규 도메인의 OAuth 콜백, 쿠키, CORS 설정을 검증한다.
- [ ] v1·v2 API와 데이터의 공존 및 호환성을 확인한다.
- [ ] 도메인 변경 후 재로그인과 기존 독서 기록 접근을 검증한다.
- [ ] v2 앱의 버전·빌드 번호 및 신규 운영 URL을 설정한다.
- [ ] 실제 구버전 앱은 v1, 신규 앱은 v2를 여는지 검증한다.
- [ ] v1의 정확한 종료일과 업데이트 안내를 준비한다.
- [ ] 심사에 필요한 서비스 접근과 로그인 계정을 준비한다.
