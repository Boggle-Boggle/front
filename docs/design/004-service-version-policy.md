# 통합 서비스 버전 관리 정책

## 목적과 결정

웹과 네이티브를 포함한 빼곡 서비스의 변경을 하나의 사용자용 서비스 버전으로 관리한다. 서비스 버전과 통합 릴리스 노트의 단일 기준(SSOT)은 `front`에 둔다.

웹과 앱에 독립적인 사용자용 버전 체계를 만들지 않는다. 웹만 배포하면 서비스 버전만 변경하고, 네이티브 앱을 출시할 때는 해당 출시의 서비스 버전을 앱 버전으로 사용한다.

이 문서는 합의한 정책이다. 서비스 버전은 `package.json`에 저장하고, 통합 릴리스 노트는 `docs/releases/{버전}.md`에 보관한다. 앱 빌드로의 버전 전달과 웹 배포 커밋 기록 자동화는 후속 구현 대상이다.

## 버전 증가 규칙

서비스 버전은 `MAJOR.MINOR.PATCH` 형식으로 관리한다. 변경 대상이 웹인지 네이티브인지보다 사용자에게 제공되는 변경의 규모를 기준으로 판단한다.

| 자리 | 증가 기준 | 예시 |
| --- | --- | --- |
| MAJOR | 서비스의 큰 개편 | `2.4.3 → 3.0.0` |
| MINOR | 사용자 관점에서 의미 있는 기능 추가 | `2.1.2 → 2.2.0` |
| PATCH | 작은 개선, 오류 수정, 작은 네이티브 개선 | `2.1.1 → 2.1.2` |

상위 자리를 올리면 하위 자리는 0으로 초기화한다. 하나의 출시에는 포함된 변경 중 가장 큰 규모를 적용한다. 작은 기능성 개선도 PATCH로 분류할 수 있으며, 구체적인 변경 내용은 릴리스 노트로 설명한다.

이는 서비스의 출시 규모를 표현하는 팀 규칙이다. 버전 숫자만으로 API 또는 네이티브 호환성을 보장하거나 판단하지 않는다.

## 웹 배포와 앱 출시 관계

| 배포 내용 | 서비스 버전 | 새로 출시하는 앱 버전 | 스토어 최신 앱 버전 |
| --- | --- | --- | --- |
| 최초 출시 | `2.0.0` | `2.0.0` | `2.0.0` |
| 웹 오류 수정 | `2.0.1` | 없음 | `2.0.0` |
| 웹 기능 추가 | `2.1.0` | 없음 | `2.0.0` |
| 작은 웹 개선 | `2.1.1` | 없음 | `2.0.0` |
| 작은 네이티브 개선 | `2.1.2` | `2.1.2` | `2.1.2` |

앱 버전은 `2.0.0 → 2.1.2`처럼 중간 서비스 버전을 건너뛸 수 있다. 웹만 변경했다고 앱 빌드나 스토어 제출을 수행할 필요는 없다.

네이티브 기능 추가가 크다면 MINOR를, 작은 개선이라면 PATCH를 올린다. 앱 버전의 마지막 자리를 0으로 고정하지 않는다.

표의 스토어 최신 앱 버전과 사용자 기기에 설치된 앱 버전은 다를 수 있다. 웹 배포나 스토어 업데이트 공개만으로 이미 설치된 앱의 버전은 바뀌지 않는다.

## SSOT와 각 정보의 책임

| 정보 | 기준 | 용도 |
| --- | --- | --- |
| 서비스 버전 | `front/package.json`의 `version` | 사용자 표시, 통합 출시 식별 |
| 통합 릴리스 노트 | `front/docs/releases/{버전}.md` | 웹·네이티브 변경 이력 |
| 앱 출시 버전 | 해당 출시를 위해 확정한 서비스 버전 | 스토어에 제출할 앱 버전 |
| 설치된 앱 버전 | 실제 네이티브 빌드 정보 | 문제 진단, 앱 식별 |
| 앱 빌드 번호 | EAS 원격 관리 및 자동 증가 | 동일 앱 버전의 빌드 구분 |
| 웹 배포 커밋 | 실제 배포한 Git 커밋 | 배포 추적, 문제 재현 |

앱 설정에 반영하는 버전은 `front`에서 확정한 출시 버전의 복사본이다. 앱 저장소에서 별도의 규칙으로 서비스 버전을 결정하지 않는다. 구체적인 전달 및 검증 방법은 구현 시 정한다.

앱을 빌드할 때는 대상 서비스 버전과 웹 커밋을 고정한다. 빌드 시점의 변경 가능한 최신 브랜치를 무조건 읽어 버전을 정하지 않는다. 심사 중 후속 웹 배포가 이루어져도 이미 만든 앱 빌드의 버전은 그대로 유지한다.

설치된 앱 버전을 웹의 서비스 버전으로 추정하거나 덮어쓰지 않는다. 필요한 경우 브리지로 실제 앱 정보를 받는다.

## 사용자 표시와 릴리스 기록

마이페이지의 대표 버전은 현재 웹 배포의 서비스 버전이다.

```text
서비스 버전 2.1.2
```

문제 확인을 위한 상세 정보에는 실제 앱 버전, 빌드 번호, 웹 배포 커밋을 별도로 제공할 수 있다.

```text
서비스 버전 2.1.2
설치된 앱 2.0.0 (빌드 42)
웹 배포 커밋 abc1234
```

일반 브라우저 또는 브리지 미연결 상태에서는 설치된 앱 버전을 알 수 없는 것으로 처리한다. 서비스 버전을 대신 넣지 않는다.

릴리스 노트에는 버전, 배포일, 기능·개선·수정 내용, 웹 배포 커밋, 네이티브 출시 포함 여부를 기록한다. 앱을 함께 출시했다면 플랫폼별 앱 버전과 빌드 번호도 연결한다.

```text
2.1.2
- 개선: 네이티브 키보드 동작 개선
- 수정: 독서 기록 화면의 간격 오류 수정
- 웹 커밋: abc1234
- 앱 출시: 포함
- 앱 버전: 2.1.2
- 플랫폼별 빌드 번호: 실제 출시 빌드 기준으로 기록
```

스토어 릴리스 노트는 앱 출시 때 갱신한다. 웹 단독 배포 이력은 웹의 통합 릴리스 노트에 기록한다. 스토어의 버전과 마이페이지의 서비스 버전이 다를 수 있는 것은 정상이다.

## 호환성 관리

서비스 버전은 출시 식별자이며 실행 환경의 기능 지원 여부를 의미하지 않는다. 예를 들어 서비스 `2.1.2`를 보는 사용자가 여전히 앱 `2.0.0`을 실행할 수 있다.

- 웹과 네이티브의 호환성은 브리지 규약과 실제 지원 기능을 기준으로 판단한다.
- 웹과 백엔드의 호환성은 웹이 사용하는 API 계약을 기준으로 관리한다.
- 새로운 네이티브 기능이 없는 앱에는 대체 동작 또는 명시적인 업데이트 안내를 제공한다.
- 브리지 응답이 없다는 이유만으로 특정 앱 버전이나 API 계약을 추정하지 않는다.
- 호환성이 깨지는 변경은 버전 증가만으로 해결되지 않는다. 구 계약 유지, 전환 순서 및 지원 종료 계획을 별도로 정한다.

브리지 메시지 형식, 지원 기능 목록, 최소 지원 앱 정책 및 API 전환 방식은 후속 설계 대상으로 둔다.

## 출시 흐름

1. 변경 규모에 따라 다음 서비스 버전을 결정한다.
2. `front`에서 버전과 통합 릴리스 노트를 함께 준비한다.
3. 검증한 웹 커밋과 출시 버전을 확정한다.
4. 웹 단독 변경이면 웹을 배포하고 배포 이력을 기록한다.
5. 앱 출시가 포함되면 확정한 버전을 앱에 반영하고 EAS가 빌드 번호를 증가시키도록 한다.
6. 앱 심사와 배포에 맞춰 웹 공개 시점을 조정하고, 이전 앱에서도 새 웹의 대체 동작이 유효한지 확인한다.
7. 실제 웹 배포와 플랫폼별 앱 출시 결과를 기록한다.

브랜치와 도메인 운영은 [v2 출시와 v1 유지 기간의 브랜치·배포 전략](./003-v2-release-branch-strategy.md)을 따른다. 브랜치 이름 자체를 서비스 버전으로 사용하지 않는다.

- [x] 통합 릴리스 노트의 파일 형식 및 보관 위치: `docs/releases/{버전}.md`
- [ ] 확정된 서비스 버전을 앱 빌드에 전달하고 검증하는 방법

- [ ] 마이페이지의 버전 표시와 진단용 상세 정보 범위
- [ ] 실제 앱 정보와 지원 기능을 전달하는 브리지 계약
